# 引用与知识关系

知识文件中的事实必须能回到 `raw/` 里的原始资料。`sources` 是系统维护的来源集合；正文脚注负责把具体论断定位到具体来源位置。

## 脚注格式

使用 Obsidian/Markdown 命名脚注：

```markdown
SQLite 在本项目中只是可重建索引。[^raw_01HZX-1]

[^raw_01HZX-1]: locator: 第 3 节“数据边界”；note: 明确区分索引与事实文件
```

- 脚注名以真实 raw ID 开头；同一来源多处引用可追加 `-1`、`-2`。
- `locator` 必须足以重新找到证据，可写页码、章节、时间戳、行号、提交号或 URL 片段。
- `note` 只说明引用与论断的关系，不改写或扩张原始证据。
- 无法定位时明确写 `locator: 未提供`，并把该知识标记为待复核，不得伪造位置。

CLI 发布校验会拒绝不存在的 raw ID、无定义的引用、未使用的脚注和缺少 locator 的定义。CLI 无法仅靠语法判断哪些句子是“关键事实”；Agent 与审批者必须确认每个关键论断附近确有足够证据，不能把通过语法校验误解为事实已经被自动证明。

## 冲突证据

来源相互冲突时：

1. 同时引用支持与反对来源。
2. 在正文解释适用条件、时间范围或口径差异。
3. 冲突尚未解决时使用 `lifecycle: disputed`。
4. 不以“多数来源”自动覆盖质量更高或时间更新的来源。

## 知识关系

`related`、`supersedes`、`superseded_by` 必须写为能解析到实际文件的 Obsidian 链接：

```yaml
related:
  - "[[knowledge/concept/发布提案--know_01HZY|发布提案]]"
```

- 链接路径包含稳定 ID，不能只写标题或虚构目标。
- `related` 表示语义关联，不表示证据来源。
- 证据只通过 raw ID 与脚注表达，不把 raw 文件塞入 `related`。
- 替代关系必须双向一致，普通关联是否双向由语义决定。
